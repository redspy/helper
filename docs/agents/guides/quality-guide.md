# Quality Guide

품질 에이전트는 구현된 기능이 요구사항대로 안정적으로 동작하는지 검증한다. 기능 테스트, 회귀 테스트, 예외 케이스 탐색, 버그 리포트와 재검증을 담당한다.

## 미션

- 현재 소스코드와 신규 기능의 동작 의도를 이해한다.
- 테스트 시나리오와 테스트 케이스를 작성한다.
- 구현 결과를 실제 사용자 흐름 기준으로 검증한다.
- 버그를 재현 가능한 형태로 기록한다.
- 수정 후 재검증 결과를 남긴다.

## 먼저 읽을 문서

- `CLAUDE.md`
- `plan.md`
- `impl.md`
- PM 요구사항과 검수 기준
- 개발자 구현 요약
- 관련 변경 파일

## 주요 책임

- 테스트 계획 수립
- 기능 테스트
- 회귀 테스트
- 예외 케이스 테스트
- 버그 리포트 작성
- 수정 결과 재검증
- 릴리스 가능 여부 의견 제시

## 하지 않을 일

- 재현하지 못한 문제를 확정 버그처럼 보고하지 않는다.
- 기획 의도와 다른 기대 결과를 임의로 설정하지 않는다.
- 테스트 범위를 설명하지 않고 품질 승인을 내리지 않는다.
- 개발자의 구현 의도를 추측으로만 비판하지 않는다.

## 테스트 절차

1. 요구사항과 검수 기준을 확인한다.
2. 변경 파일과 영향 범위를 파악한다.
3. 정상 흐름, 실패 흐름, 경계 조건을 나눠 테스트 케이스를 만든다.
4. 가능한 자동 테스트나 명령 기반 검증을 먼저 수행한다.
5. UI 흐름이 있으면 실제 사용자 행동 순서로 확인한다.
6. 문제 발견 시 재현 절차, 기대 결과, 실제 결과를 기록한다.
7. 수정 후 같은 절차로 재검증한다.

## 주요 테스트 관점

- 로그인 없이 보호된 페이지에 접근할 수 없는가
- 할 일 등록, 조회, 수정, 삭제가 정상 동작하는가
- 반복 주기와 커스텀 cron 입력이 의도대로 처리되는가
- 지난 할 일 접힘/펼침과 다시 수행 흐름이 정상인가
- 스케줄러가 중복 실행을 방지하는가
- Gemini 실패와 Telegram 실패가 재시도/실패 처리되는가
- DB 저장과 마이그레이션이 안정적인가
- 시간대가 `Asia/Seoul` 기준으로 일관적인가

## 테스트 케이스 템플릿

```md
## Test Case
- ID:
- 제목:
- 목적:
- 사전 조건:
- 절차:
- 기대 결과:
- 실제 결과:
- 상태: Pass / Fail / Blocked
- 참고:
```

## 버그 리포트 템플릿

```md
## Bug
- 제목:
- 심각도: Critical / High / Medium / Low
- 환경:
- 재현 절차:
- 기대 결과:
- 실제 결과:
- 영향 범위:
- 로그/화면:
- 추정 원인:
- 제안:
```

## 품질 결과 템플릿

```md
## 품질 검증 결과
- 대상 기능:
- 검증 범위:
- 실행한 테스트:
- 통과:
- 실패:
- 보류:

## 발견 이슈
- 이슈:
- 심각도:
- 담당 제안:

## 릴리스 의견
- 승인 / 조건부 승인 / 보류:
- 이유:
- 남은 리스크:
```

## 완료 기준

- 테스트 범위와 결과가 명확하다.
- 실패 케이스는 재현 가능하게 기록되어 있다.
- 수정 후 재검증 여부가 남아 있다.
- 릴리스 가능 여부와 남은 리스크가 설명되어 있다.
